# 达人研究与四段式选题规格

## 1. 先从 live brief 建约束表

每批提取：

```text
brief_title / revision / active_dates
target_people / creator_profiles
promoted_skills / forbidden_or_unavailable_skills
required_final_artifacts
platform_rules
topic_or_prompt_wording_rules
user_overrides
```

活动主题、受众和能力会变化，不能把上次“开学季”答案当长期规则。配置只固定 brief URL。

当前 brief 的通用质量信号应每次现场确认：不是只给文字建议，最终要形成网页/小程序、可复用稳定工作流，或 PPT + Excel + 文档等组合产物；具体以 live revision 为准。

## 2. 主页研究

候选达人至少看近 20 条可访问作品；低频账号看最近一个完整内容周期。记录：

```text
真实身份/经历及证据链接
主要内容方向和近期开题分布
真人出镜证据（若 brief 需要）
高互动内容与常用呈现形式
粉丝反复出现的问题
本人明确表达的工作/学习痛点
自然电脑场景
不适合方向与原因
```

证据优先级：主页简介 > 本人近期作品 > 置顶/系列内容 > 评论区反复问题 > 机构备注。昵称或机构大类不能代替身份。

平台未登录、验证码、风控、游客态残缺时，暂停该平台研究并标 `NEEDS_EVIDENCE`；不能用搜索摘要证明“没有相关内容”。

## 3. 外部案例与真实痛点

每个主要候选方向至少收集：

- 3 个近 12 个月的相邻 AI/工作流/内容案例；
- 5 条目标人群真实吐槽、求助或经验表达；
- 1 个相比现有解决方式的明确升级点。

回答四个问题：现在怎么做、哪一步最耗时/易错、现有工具为什么不够、豆包最后交付什么。优先官方一手源与用户原生内容；二手汇总只找线索。

研究是为了写准，不是加严淘汰。找不到“爆款”不能单独作为拒绝理由，但找不到真实身份或真实需求必须降级为补证/改题。

## 4. PC 与 Skill 路由

至少命中两项：

- PC-1：自然发生在电脑前；
- PC-2：需要表格、文档、图表或 15 个以上信息点；
- PC-3：需要多窗口、多文件、大量键盘输入或反复操作。

先列能力动作，再对照 `doubao-task-mode-cases/references/能力地图.md` 选 Skill。一个题以一个主 Skill 为核心，辅助 Skill 只补必要环节。

生命周期：

- 看懂/探索一次：可视化；
- 反复操作、保存状态、协作或持续迭代：应用生成；
- 清洗、匹配、计算 Excel/CSV：表格/Office；
- 多文档提取、比较、正式成稿：文档/Office；
- Lark 是数据与交付层，不单独当宣传主角。

同一个 Skill 可以服务多个不同达人和不同任务。不得因 Skill 重复直接淘汰。

## 5. 四段式固定格式

只能使用以下标签和顺序：

```text
身份：[主页可证实的身份，一句话]
功能：[1 个主 Skill；必要时加 1 个辅助 Skill]
痛点 / 场景：[简单写清具体时刻、输入资料和失败代价]
具体实现与步骤：[输入什么 → 豆包做什么 → 最终得到什么；必要时补人工复核]
```

简洁要求：

- 每段一行、一句；
- 单元格整体以 100–220 个中文字符为宜，超过 260 个字符校验失败，必须压缩；
- 不写研究过程、传播口号、长背景、方法论解释或 Skill 功能清单；
- `痛点 / 场景` 只留简单真实痛点；
- `具体实现与步骤` 必须含最终产物，不能停在“整理/分析”；
- 不承诺豆包代做专业决策。

合格示例：

```text
身份：跨境电商 Listing 优化博主
功能：浏览器任务 Skill + 文档 Skill
痛点 / 场景：每次上新都要在多个竞品页面和表格间来回核对关键词、卖点和合规表述，版本一多就容易漏改。
具体实现与步骤：克隆 GitHub 上的 Listing 优化工作流，录入产品资料后由豆包抓取并对照竞品页面，生成带关键词依据、风险标记和可直接复核的 Listing 文档。
```

不合格示例：

```text
身份：职场博主
功能：应用生成 Skill
痛点 / 场景：工作效率低，资料很多。
具体实现与步骤：把资料给豆包，豆包生成一个好看又实用的系统。
```

## 6. 查重记录

为每条候选题写结构化字段：

```text
main_skill（路由依据，不进入完全重复键）
core_task
key_input
final_artifact
lifecycle
historical_match
```

只把 `core_task + key_input + final_artifact/lifecycle` 实质相同判为完全重复。标题措辞不同不算新题；主 Skill 相同、但任务或产物不同则允许。每批把可访问的历史题全量结构化为 `history.duplicate_keys`，并标记 `snapshot_complete=true`；`history.sources` 每个来源记录 URL、正 revision、扫描行数和内容 SHA-256。同批 SUBMIT 键不得互相重复，也不得存在于历史键集。

## 7. 写前清单

```text
[ ] 身份来自主页或本人作品，不是昵称猜测
[ ] 符合本次 brief 的人群、能力、时间窗和产物
[ ] 无当前/历史业务阻断
[ ] PC-1/2/3 至少两项
[ ] Skill 路由和生命周期正确
[ ] 与历史题不完全重复；仅 Skill 相同未被误杀
[ ] 四个标签齐全且顺序正确
[ ] 痛点简单具体，步骤写到最终产物
[ ] 总长度已压缩
```
